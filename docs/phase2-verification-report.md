### Bug found and fixed during Task 4

The first `alembic upgrade head` attempt failed with:

```
sqlalchemy.exc.ProgrammingError: (psycopg.errors.UndefinedObject) type "parametersourcetype" does not exist
```

**Root cause:** this is a known Alembic/PostgreSQL limitation. When
SQLAlchemy creates a brand-new table with an Enum column, it auto-creates
the Postgres `ENUM` type as part of `CREATE TABLE`. But when an Enum
column is added to an *existing* table via a standalone `op.add_column`
(as with `machine_parameters.source_type`), Alembic does not automatically
emit a `CREATE TYPE` statement first. (`expected_data_source` didn't hit
this because it reuses the `datasource` enum type, which already existed
from Phase 1's `sensor_readings.source` column.)

**Fix:** two explicit lines added to the autogenerated file (which is
templated with `# please adjust!` for exactly this kind of case) — one
creating the enum type before the `add_column` call in `upgrade()`, one
dropping it after the column removal in `downgrade()`. This is a standard,
documented pattern for this situation, not a custom migration authored
from scratch — the surrounding 95% of the file is still pure autogenerate
output.

**Verified:** Postgres's transactional DDL rolled back the first failed
attempt cleanly — `\dt` after the failure showed no partial state
(`sensor_calibrations` absent, `machine_parameters` unchanged). After the
fix, the migration applied cleanly, was confirmed reversible via
`downgrade -1`, and was proven to work against both an existing database
(incremental upgrade) and a completely fresh one (full chain from `<base>`).

A second, unrelated bug was also found and fixed during this process: a
Notepad paste stripped the leading indentation from the `op.add_column`
line for `source_type`, which would have caused a Python `IndentationError`
if run as-is. Caught via `python -m py_compile` before touching the
database, and fixed with a precise PowerShell regex replace rather than
another manual paste.
